# Local capstone threat model

Assets: synthetic runbooks, tenant scope, action authority, demo token and request ledger. Trust boundaries: HTTP client to service, service to fixtures and SQLite ledger, proposed tool to application policy. The service binds to loopback and requires a demo bearer token for investigation and metrics. The token is shared process configuration, not real user identity. It is bound to the fixed `demo` tenant; a different caller-supplied tenant is denied.

The request ledger stores result data and a hash of the question, not the raw question or token. A hash can still reveal a low-entropy question by guessing, so the retention command and local-only synthetic-data rule matter. A repeated request ID with different tenant or question is denied; a matching retry returns the recorded result. Concurrent first requests with the same ID can both compute before one record is inserted, so this local read-only path must not be reused for real side effects without a stronger reservation/transaction design.

This is not real user authentication or multi-tenant authorization. A production service would require authenticated identity, tenant authorization, durable approval for real effects, rate limits, audit retention policy, TLS at the appropriate boundary, release rollback automation and operational monitoring. Model or retrieved text must never grant tool permission. Do not expose this reference service publicly.
